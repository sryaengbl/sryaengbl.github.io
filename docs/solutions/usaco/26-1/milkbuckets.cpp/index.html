Analysis

personally a pretty difficult question it was apparent that the optimal strategy was to make the array unimodal. however, actually doing this was nontrivial. my intuition for the problem was to process the values in increasing order this meant finding a "pivot" element and then building the array by adding elements either to the left or to the right of that pivot i originally thought that it would be optimal for elements to stay on the side of the pivot that they originally appeared in. however, the last test case proved that this is incorrect then i considered how to evaluate the cost of keeping an element on the left side versus the right side. however, this was quite difficult because swaps could happen if the element was too large or too small it wasn't clear to me how this could be faster than o(n^2), especially because even if we process smallest to largest, it's easily possible that an element must swap with a larger element, blowing up the complexity i also thought about how to approach the problem with inversions, since rearranging an array is adjacent to sorting it, and sorting an array with swaps is characterized by the inversions, the classic invariant for it. nonetheless, to make the array unimodal, it's true that the right side will have 0 inversions and all inversions must come from the left side however, this still doesn't really give us instructions for how to actually build an optimal array. the observation that the editorial makes is to realize that we can simply consider a "swap" to be swapping an element with strictly smaller elements. in any pairwise swap, one element must be smaller (equal elements aren't worth swapping) so it's safe to count swaps purely from the perspective of the larger element that solves the problem of needing to swap a small element with a larger one in the processing order. we still DO the swap, it's just that we count it later with this idea in mind, we don't even need to fix a pivot element we can just count the number of smaller to the left and to the right ordered set makes this trivial and an easy implementation. general takeaway is that #swaps to sort an array can be viewed purely through the perspective of the larger element.

#include <bits/stdc++.h>
using namespace std;
using ll = long long;
#ifdef LOCAL
#include "algo/debug.h"
#else
#define dbg(...) 0
#define dbgn(...) 0
#endif
#include <bits/extc++.h>
using namespace __gnu_pbds;

template <class T>
using Tree = tree<T, null_type, less<T>, rb_tree_tag, tree_order_statistics_node_update>;

void solve() {
    int n;
    cin >> n;
    vector<int> a(n);
    for (int i = 0; i < n; i++) {
        cin >> a[i];
    }
    vector<int> idx(n);
    for (int i = 0; i < n; i++) {
        idx[i] = i;
    }
    sort(idx.begin(), idx.end(), [&](int u, int v) { return a[u] < a[v]; });
    Tree<int> t;
    int c = 0;
    vector<int> upd, l(n), r(n);
    for (int i = 0; i < n; i++) {
        if (c != a[idx[i]]) {
            for (auto x : upd) t.insert(x);
            upd.clear();
        }
        c = a[idx[i]];
        l[idx[i]] = t.order_of_key(idx[i]);
        r[idx[i]] = t.size() - t.order_of_key(idx[i]);
        upd.push_back(idx[i]);
    }
    ll ans = 0;
    for (int i = 0; i < n; i++) {
        ans += min(l[i], r[i]);
    }
    cout << ans << '\n';
}

int32_t main() {
    cin.tie(0)->sync_with_stdio(0);
    int tt;
    cin >> tt;
    while (tt--) {
        solve();
    }
    return 0;
}
